# 无痕内存读写引擎 —— 超越点补充设计（Tier 体系）

> 补充日期：2026-10-11
> 关联：`docs/MEM_ENGINE_PLAN.md`（基础设计）
> 触发：用户提问「全部加上，可切换可行？然后只有这些，没有超越点了吗？」

---

## 一、回答两个问题

### 问题 1：全部加上，可切换可行？

**可行。** 但不是"一个开关切两个引擎"，而是**分层策略选择器**。

原因：`MmCopyMemory` 与自建映射不是二选一 —— 它们在**不同的层**上：

```
Layer 3  传输原语（怎么把字节搬进来）
         ├─ P1  MmCopyMemory(PHYSICAL)     ← 已验证
         ├─ P2  MmGetVirtualForPhysical    ← 仅系统页
         └─ P3  自建物理映射（PML4 镜像）   ← 彻底自主

Layer 2  访问路径（经过哪些 API）
         ├─ A   MmCopyVirtualMemory        ← 有进程语义，可被监视
         └─ B   页表遍历 + 物理帧           ← 无进程语义

Layer 1  执行位置（在哪里执行）
         ├─ Host  IOCTL 上下文（PASSIVE）
         └─ Island 岛内（DISPATCH, GIF=0） ← 完全不可观测
```

**可切换的设计**：
```c
typedef struct {
    uint8_t  layer2_path;    /* 0=auto 1=api 2=pte */
    uint8_t  layer3_xfer;    /* 0=auto 1=MmCopyMemory 2=MmGetVirtForPhys 3=selfmap */
    uint8_t  layer1_where;   /* 0=auto 1=host 2=island */
    uint8_t  _pad;
} yghv_mem_strategy_t;
```

**命令**：
```powershell
yghv_ctl.ps1 mem-strategy                      # 读当前策略
yghv_ctl.ps1 mem-strategy path=pte xfer=selfmap where=island
yghv_ctl.ps1 mem-strategy auto                 # 回到自动
```

**AUTO 的决策矩阵**（自动选层）：

| 条件 | path | xfer | where |
|---|---|---|---|
| 未加载 hypervisor | api | MmCopyMemory | host |
| 缺页/换出 | **api** | MmCopyMemory | host |
| 系统空间页 | api | MmGetVirtForPhys | host |
| 用户页 + 已加载 HV + 要求无痕 | **pte** | MmCopyMemory | **island** |
| 用户页 + 已加载 HV + 要最快 | pte | **selfmap** | island |
| 用户页 + 未加载 HV | pte | MmCopyMemory | host |
| 大页（2M/1G） | pte | 任意 | island |

**可行性结论**：
- Layer 2 切换：**完全可行**（两套代码并存，编译期都在）
- Layer 3 切换：**可行**，P1/P2 已验证，P3 是新增（Phase 2b）
- Layer 1 切换：**可行但受限** —— 岛内不能调 API（DISPATCH + GIF=0），
  所以 **island 只能配 P3 自建映射**（这正是 P3 存在的理由）

## 二、超越点体系（分三级）

### 【第一级】同层替代 —— 之前列的（仍然有效）

| # | 超越点 | 相对谁 | 量化 |
|---|---|---|---|
| 1.1 | **零 NT 内存 API** | Engine A | 调用栈无 `MmCopyVirtualMemory` |
| 1.2 | **零 CR3 切换** | Engine A | `KeStackAttachProcess` 调用数 = 0 |
| 1.3 | **大页感知** | Engine A | 2MB 一页覆盖 512 候选 → ~100× |
| 1.4 | **全类型读写**（16 种） | Engine A（裸字节） | 新增能力 |
| 1.5 | **页表驱动的扫描** | Engine A（逐地址） | 调用数 = 页数而非候选数 |
| 1.6 | **属性过滤**（可写/可执行/大页） | Engine A（无） | 跳过无用页 |

**这些是"替代"，不是"超越"** —— 因为 Engine A 也能完成同样的读写，
只是路径不同。真正的超越在下面两级。

---

### 【第二级】跨层质变 —— **真正的超越点**（新增）

#### ★★ 超越点 2.1：**岛内执行**（Hypervisor-Tier Access）

**这是什么**：把读写动作放到 **hypervisor 的 NPF 岛内**执行 —— 即
**VMEXIT 处理路径内部**（`IRQL=DISPATCH`、`GIF=0`、无锁、禁一切 NT API）。

**为什么这是质变**：
```
Host 层执行（Engine A/B）：
  调用栈：yghv_* ← MmCopyVirtualMemory ← ...   ← 可被内核 hook 看到
  进程上下文：System 进程                      ← 可被 ETW 关联

岛内执行（新）：
  调用栈：SvHandleVmExit ← 我们的裸代码         ← **宿主内核看不到我们**
  进程上下文：**guest 的上下文**（不是 System） ← ETW 关联到 guest
  GIF=0：中断被屏蔽，**没有任何外部观察者能插入**
```

**关键**：**宿主内核对岛内执行的代码"不可见"** —— 因为代码运行在
**VMRUN 之后的 guest 上下文里**，宿主内核的调度器、ETW、栈回溯
**都不覆盖这个执行域**。

**技术可行性**（已核实）：
- 现有 `yghv_protect_on_npf_write_bare` **已在岛内运行**（lock-free、纯内存）
- `MmGetVirtualForPhysical` **无 IRQL 限制** → 页表遍历可在 DISPATCH 做
- 岛内约束：不能调 `MmCopyMemory`（那是 API）→ **必须用 P3 自建映射**

**实现路径**：
```
1. 触发：guest 里某个"看似无害"的指令（如对特定地址的读）
2. NPF 拦截 → 岛内代码执行
3. 岛内：用 P3 自建映射读目标物理帧 → 结果写入**共享页**
4. 返回 guest → guest 从共享页取结果
```

**这是"超越"的核心**：不是"用另一条路读写"，而是**在宿主看不到的地方读写**。

---

#### ★★ 超越点 2.2：**自建物理映射**（Self-Mapped Physical Window）

**这是什么**：不走 `MmCopyMemory`，而是**自己维护一个 PML4 镜像**，
把目标物理帧映射进自己的地址空间，然后**直接解引用**。

**为什么是质变**：
```
MmCopyMemory 路径：
  MmCopyMemory → MiDoPoolCopy → 内部 memcpy    ← 全程可 hook
  且每次调用都要走一遍 API 的参数校验/分发

自建映射路径：
  ① 初始化时：分配一页 PML4，写一个 PTE 指向目标帧
  ② 读：`*(volatile uint8_t*)window`            ← **一条 mov 指令**
  ③ 改目标：改写 PTE 指向另一帧（改一个 8 字节）
```

**性能质变**：
| 操作 | `MmCopyMemory` | **自建映射** |
|---|---|---|
| 读 4KB | ~2.97 μs（实测） | **~0.1 μs**（纯内存访问） |
| 读 1 字节 | 同 4KB（有固定开销） | **~10 ns** |
| 连续读同页 1000 次 | 1000 次 API | **1 次映射 + 1000 次 mov** |

**技术风险与应对**：
- ⚠️ 自建 PML4 必须与系统页表共存 → 用**独立的 PML4**（不改系统的）
- ⚠️ 切换 CR3 会影响当前执行 → **只用于岛内**（岛内已在 guest 上下文，可控）
- ⚠️ 缓存属性（PAT/MTRR）→ 用 `MmNonCached` 或与目标一致

---

#### ★★ 超越点 2.3：**保护 + 读写一体**（Protection-Aware Access）

**这是什么**：读写引擎**感知保护状态** —— 对**已被周期同步守卫保护**的页，
读写**不触发回滚**。

**为什么是质变**：
```
现状：守卫保护页 P → 我们写 P → 守卫检测漂移 → **回滚我们的写**  ← 冲突！
      （9.304 B3d 实测：目标自己的合法写入也被回滚）

新能力：读写引擎知道 P 被保护 →
  ① 写入前：把 P 的快照**同步更新**（写进快照）
  ② 写入后：守卫比对时看到"快照 == 当前" → **不回滚**
  ③ 结果：我们的写**持久生效**，且守卫继续保护其它写
```

**这是"1+1>2"**：单独的读写引擎和单独的守卫引擎都做不到这件事 ——
**只有两者协同才能实现"受保护页的定向写入"**。

**实现**：
```c
/* 写受保护页时的正确姿势 */
NTSTATUS yghv_mem_write_protected(uint64_t gpa, const void *src, SIZE_T len) {
    /* ① 写物理帧 */
    yghv_pa_write(gpa, src, len);
    /* ② 同步守卫快照（否则下一轮被回滚） */
    yghv_protect_sync_refresh(gpa);   /* 新增：重拍快照 */
    return STATUS_SUCCESS;
}
```

#### ★★ 超越点 2.4：**零拷贝双向共享窗**（Zero-Copy Shared Window）

**这是什么**：在 guest 与 hypervisor 之间建立一个**共享物理页**，
双向读写**不需要任何数据拷贝** —— 双方直接操作同一物理帧。

**为什么是质变**：
```
现有 mmf 机制：
  目标进程写 → 守卫读 → 比对 → 回滚        ← 多次拷贝
  guest ↔ hypervisor 通信走 IOCTL          ← 系统调用 + 拷贝

共享窗：
  guest 直接读/写共享页 → hypervisor 岛内直接读/写同一页
  **零拷贝、零系统调用、零 API**
```

**用途**：批量读写的**高速通道** —— guest 侧把"要读的地址列表"写进共享页，
岛内处理后把"结果"写回同一页，guest 再读走。

**这本质上是把 IOCTL 的往返成本降到零**。

### 【第三级】能力级超越 —— 之前完全没有的能力

#### ★★★ 超越点 3.1：**隐身读取**（Stealth Read —— 不触碰目标）

**这是什么**：**不修改目标进程的任何状态**就能读到它的内存。

**为什么是质变**：
```
Engine A（MmCopyVirtualMemory）：
  → 内核可能触发缺页处理 → 可能修改目标 PTE（设为 accessed/dirty 位）
  → 可能触发 COW 分裂 → **目标的内存布局被改变**

Engine B（页表遍历 + 物理帧读）：
  → 只读 PTE（不写）→ PTE 的 accessed 位**不会被设置**
  → 读物理帧 → 不触发任何 fault
  → **目标进程完全不知道自己被读过**
```

**关键细节**：读 PTE **不会**设置 A/D 位（只有 CPU 的页表遍历会）；
我们手工读 PTE 内存，CPU 不参与 → **零痕迹**。

**这是真正的"无痕"** —— 之前的"无痕"只是"不被 hook 看到"，
这个是**"目标完全无感知"**。

---

#### ★★★ 超越点 3.2：**反检测的读写模式**（Evasion-Aware Access）

**这是什么**：读写操作**主动规避已知的检测手法**。

| 检测手法 | 规避方式 |
|---|---|
| 检测 PTE 的 accessed 位被异常置位 | 手工读 PTE 不置位（3.1 已达成） |
| 检测目标页的 dirty 位 | 写入后**恢复 dirty 位原值** |
| 检测内存内容被非预期修改 | 提供 `--snapshot-first`（改前存快照，可回滚） |
| 检测 EPROCESS 引用计数异常 | 不长期持有进程引用（用完即放） |
| 检测 CR3 切换频率 | 零切换（Engine B 天然满足） |
| 检测异常的内核栈模式 | 岛内执行（栈不在宿主可见范围） |

**量化目标**：PTE 的 A/D 位在读写前后**逐位一致**。

---

#### ★★★ 超越点 3.3：**跨进程特征码扫描的页表级优化**

之前提了"大页感知"，但还有更深的三层：

**① 页表级预筛**：
```
遍历页表时，PTE 自带属性：
  - present 位 → 跳过未映射（通常省 50-80% 空间）
  - 大页位   → 2MB 一页覆盖 512 候选
  - NX 位    → 按需求跳过不可执行页
  - dirty 位 → 只扫被写过的页（找"最近修改"的特征码）
```
**Engine A 完全做不到这个** —— 它只能逐地址问"这里有没有"。

**② 共享页去重**：
```
多个进程/多个映射可能指向**同一物理帧**（共享内存、DLL 代码段）
→ 用 PA 做 key 去重 → **同一物理页只扫一次**
→ 扫描 DLL 密集的进程时，省 30-60%
```

**③ 反向扫描（从物理到虚拟）**：
```
常规：VA → 遍历 → PA → 读 → 匹配
反向：已知 PA（如从别处得到的）→ 反查所有映射它的 VA
```
**这个 Engine A 根本不可能做**（它只有 VA 接口）。

---

#### ★★★ 超越点 3.4：**写时保护协同**（Write-Protected Write）

**这是什么**：在**页面被 NPT 标记为只读**的情况下完成写入。

**为什么是质变**：
```
现状：NPT 把页标为 PRESENT-only（不可写）→ 任何写触发 NPF → 裁决
新能力：我们的引擎**知道**这个页被保护 →
  → 直接写物理帧（绕过 NPT！NPT 只约束 CPU 的 guest 访问）
  → NPT 的权限对**我们的物理帧写**无效
```

**这是虚拟化层的独特优势**：NPT 约束的是 **guest 的 CPU 访问**，
而 hypervisor **直接操作物理帧**时不受 NPT 约束。

**用途**：受保护页的**合法写入**（如补丁注入），且**不触发 NPF 裁决**。

## 六、风险重估（加了超越点之后）

| Phase | 原风险 | 新风险 | 说明 |
|---|---|---|---|
| 2b 自建映射 | — | **中高** | 自管 PML4，CR3 切换风险 |

**建议**：Phase 6 **最后做**，且**先做只读**（岛内读 → 共享页），
验证通过再做写入。

## 七、修订后的"超越"承诺

相对 **Engine A（`MmCopyVirtualMemory`）**：

| 维度 | Engine A | 本设计（完整） |
|---|---|---|
| NT 内存 API | 调用 | **零** |
| CR3 切换 | 有 | **零** |
| 执行域 | 宿主内核 | **可选岛内**（宿主不可见） |
| 传输原语 | 内核实现 | **自建映射**（一条 mov） |
| 目标感知 | 可能触发缺页/COW | **完全无感知**（A/D 位不变） |
| 保护冲突 | 写入被守卫回滚 | **协同**（写入持久） |
| NPT 约束 | 受约束 | **不受约束**（物理帧直写） |
| 扫描 | 逐地址 API | **页表驱动 + 去重 + 反向** |
| 类型 | 裸字节 | **16 种** |
