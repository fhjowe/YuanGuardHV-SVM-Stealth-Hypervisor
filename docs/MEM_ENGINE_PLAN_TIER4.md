# 无痕内存引擎 —— 第三批补充：虚拟化层独有的"狠"能力（Tier 4）

> 补充日期：2026-10-11
> 关联：`MEM_ENGINE_PLAN.md`（基础）+ `MEM_ENGINE_PLAN_TIER2.md`（Tier 1/2/3）
> 触发：用户提问「全部纳入，还有没有给狠的」

---

## 前置：前三级的定位

| 级别 | 性质 | 举例 |
|---|---|---|
| Tier 1 | **同层替代** | 零 API、零 CR3 切换、大页感知 |
| Tier 2 | **跨层质变** | 岛内执行、自建映射、保护协同、零拷贝窗 |
| Tier 3 | **能力级新增** | 隐身读取（A/D 位不变）、反检测、扫描优化 |

**这三级的共同点**：都还在"**读写内存**"这件事上做文章。

**Tier 4 不同** —— 它是**虚拟化层独有的、宿主内核原理上做不到的能力**。
不是"更快/更隐蔽的读写"，而是"**读写之外的事**"。

## ★★★ 4.1 视图分裂（Split-View Memory）—— **最狠的一个**

### 这是什么

**同一个 guest 物理地址，对不同的观察者呈现不同的内容。**

```
                    guest 进程 A 读 VA X
                          ↓
                    NPT 翻译 GPA G
                          ↓
            ┌─────────────┴─────────────┐
            │  谁在读？                  │
            ├───────────────────────────┤
            │ 目标进程（游戏/被保护者）  → 真实物理帧 R
            │ 我们的读取引擎             → 影子帧 S（我们控制的副本）
            │ 反作弊/检测器             → 影子帧 S
            └───────────────────────────┘
```

**机制**（已核实可行）：
- 我们**已有两套 NPT**（`g_npt` 主 + `g_npt_alt` 影子）
- `npt_map_page(m, gpa, spa, flags)` 可以把**任意 GPA 映射到任意 SPA**
- **VMEXIT 时按"当前是谁在访问"选择用哪套 NPT**

### 为什么这是"狠"的

| 能力 | 宿主内核能做到吗 |
|---|---|
| 让目标进程看到真实内存 | 能 |
| 让检测器看到伪造内存 | **不能** —— 宿主里"内存就是内存"，没有"按观察者分裂"的概念 |
| 两者同时成立 | **原理上不可能** —— 只有 hypervisor 在翻译层才能做 |

### 具体用途

**用途 A：检测器对抗**
```
反作弊读游戏内存做校验 → 走 alt NPT → 读到我们准备的"干净副本"
游戏自己读写 → 走主 NPT → 真实内存
→ 校验永远通过，而真实内存已被我们修改
```

**用途 B：蜜罐内存**
```
检测器扫描"可疑修改" → 我们在影子帧里放**看起来正常**的内容
→ 检测器找不到异常 → 而我们能在真实帧里做任何事
```

**用途 C：条件视图**
```
按访问来源（哪个 CR3、哪个 RIP 范围、cpl）决定看到什么
→ 细粒度到"哪条指令读到什么"
```

### 技术风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **性能** | 每次 NPF 都要判断"谁在访问" | 用 per-VCPU 状态缓存判断结果 |
| **一致性** | 影子帧与真实帧的同步 | 只在被保护页上用（不是全局） |
| **Zen3 TLB** | NPT 切换的 TLB 问题（已知：不响应软件冲刷） | ⚠️ **这是最大障碍** —— 见下 |
| **复杂度** | 需要维护"谁是谁"的判定 | 限定场景（只对已注册目标） |

> ⚠️ **关键约束**：9.297/9.298 已证 **Zen3 的 NPT 翻译不响应软件冲刷**。
> 这意味着"切换到 alt NPT"后，**已缓存的翻译不会立即失效**。
>
> **但这不否定视图分裂** —— 因为：
> 1. 现有的 C6 假写路线**就是靠 alt NPT 实现的**（虽然延迟高）
> 2. **周期同步守卫的思路可以复用**：不用 TLB 切换，而是**轮询修正**
> 3. 或者：**在建立映射时就决定**（不同的 GPA 范围用不同的 NPT 视图，
>    而不是同一个 GPA 动态切换）
>
> **建议**：先做**静态视图分裂**（不同地址范围不同视图），
> 动态切换作为后续研究。

## ★★★ 4.2 时间维度操作（Time-Dimension Control）

### 这是什么

**回滚目标内存到任意历史时刻**，或**预演未来的写入**。

```
t0: 目标页内容 = V0
t1: 我们写入 V1（目标看到 V1）
t2: 触发"回滚" → 目标看到 V0（但我们知道 V1）
t3: 再触发 → 目标看到 V1
```

### 机制

```
① 保留多份物理帧副本（V0, V1, V2...）
② npt_map_page 把 GPA 指向不同的副本
③ 切换 = 改一个 NPT 项（不拷贝任何数据）
```

### 为什么这是"狠"的

| 能力 | 宿主内核 |
|---|---|
| 保存内存快照 | 能（拷贝） |
| **瞬间回滚**（O(1)，不拷贝） | **不能** —— 拷贝 4KB 至少 4KB 的时间 |
| **同一进程内存的多个"版本"同时存在** | **不能** —— 宿主里一个 VA 只有一个内容 |
| **按指令流回滚**（执行到某处自动切换） | **不能** |

### 用途

**用途 A：无痕修改**
```
改目标内存 → 目标执行完关键逻辑 → 回滚 → 目标"没发现被改过"
（而我们已经拿到了想要的结果）
```

**用途 B：多版本测试**
```
同一份代码跑在"内存状态 A"和"内存状态 B"下，对比行为
→ 不用重启进程
```

**用途 C：反检测的时间窗**
```
检测器读内存 → 看到干净版本
我们读 → 看到真实版本
→ 按时间片切换（而非按来源）
```

## ★★★ 4.3 跨进程物理别名（Cross-Process Physical Aliasing）

### 这是什么

**让进程 A 的一个 VA 直接指向进程 B 的物理帧** —— 不需要任何 IPC、共享内存、或系统调用。

```
进程 A 读 VA 0x1000
  → 主 NPT 说：GPA 0x1000 → 物理帧 R_A
  → 但我们改写 NPT：GPA 0x1000 → 物理帧 R_B（进程 B 的页）

结果：进程 A 读自己的 0x1000，实际读到进程 B 的数据
```

### 为什么这是"狠"的

| 能力 | 宿主内核 |
|---|---|
| 共享内存 | 能（但双方必须**协商**：CreateFileMapping 等） |
| **单方面建立别名** | **不能** —— 宿主里"谁的页就是谁的页" |
| **目标进程完全不知情** | **不能** —— 共享内存双方都能看到映射 |
| **零 API、零句柄、零对象** | **不能** |

### 用途

**用途 A：零拷贝数据交换**
```
我们的引擎要读进程 B 的大块数据
→ 把目标进程的某个 VA 别名到 B 的帧
→ 目标进程直接读，零拷贝
```

**用途 B：透明注入**
```
让目标进程"看到"我们的数据（通过它自己的一个 VA）
→ 不需要 WriteProcessMemory、不需要分配内存
```

**用途 C：数据伪装**
```
目标进程读自己的配置 → 实际读到我们准备的内容
→ 它按我们的数据运行
```

## ★★★ 4.4 指令级访问控制（Instruction-Level Access Control）

### 这是什么

**同一条指令、同一个地址，从不同的 RIP 访问得到不同结果。**

```
RIP 0x1000: mov rax, [0x2000]   → 读到 V1
RIP 0x3000: mov rax, [0x2000]   → 读到 V2
```

### 机制

```
NPF 处理时，读 VMCB 的 GuestRip
→ 按 RIP 决定这次访问走哪个 NPT 视图 / 返回什么内容
```

### 为什么这是"狠"的

| 能力 | 宿主内核 |
|---|---|
| 按地址保护 | 能（页权限） |
| **按 RIP 区分同一地址** | **不能** —— 页权限是"地址级"的 |
| **对特定代码路径返回假数据** | **不能** |

### 用途

**用途 A：精准欺骗校验函数**
```
校验函数（RIP 在 0x1000-0x2000）读内存 → 假数据
游戏逻辑读同一地址 → 真数据
→ 校验通过，游戏正常
```

**用途 B：行为分析**
```
记录"哪条指令访问了哪个地址" → 完整的访问轨迹
→ 不需要任何 hook（NPF 天然带 RIP）
```

## ★★★ 4.5 物理帧所有权接管（Frame Ownership Takeover）

### 这是什么

**把某个物理帧从系统"偷走"** —— 系统回收它时我们保留内容，重新分配时给它"干净"的内容。

### 机制

```
① 标记物理帧 R 为"我们的"
② 系统释放 R（进程退出等）→ 我们保留副本
③ 系统重新分配 R → 我们让新持有者看到"清零"的内容
④ 我们随时可以读 R 的历史内容
```

### 为什么这是"狠"的

| 能力 | 宿主内核 |
|---|---|
| 内存取证 | 能（但只能在释放前） |
| **在释放后仍保留内容** | **不能** —— 释放后系统可能立刻重用 |
| **对重用者透明地伪造内容** | **不能** |

### 用途

**用途 A：取证**
```
目标进程退出 → 内存"被释放" → 但我们保留了完整内容
```

**用途 B：信息提取**
```
从"已释放"的内存里恢复敏感数据（密钥、凭据）
```

**用途 C：蜜罐**
```
释放的帧重新分配时，放入"看起来正常但实际受控"的内容
```

## ★★ 4.6 硬件断点的超集（Debug Register Superset）

### 这是什么

**远超 4 个硬件断点的限制** —— 对任意多个地址做"读/写/执行"监控。

```
现有：x86 只有 DR0-DR3（4 个硬件断点）
NPF：可以对**任意多个页**做访问监控
```

### 机制

```
npt_set_page_perm 把页设为"不可访问" → 任何访问触发 NPF
NPF 处理时记录：谁（RIP/CR3）、做了什么（读/写/执行）、访问了什么地址
→ 无限制的监控点
```

### 为什么这是"狠"的

| 能力 | 宿主内核 |
|---|---|
| 硬件断点 | 4 个 |
| **软件断点** | 需要改代码（int3）→ 可被检测 |
| **NPF 监控** | **无数量限制 + 不改代码 + 目标无感知** |

### 用途

**用途 A：完整访问轨迹**
```
监控目标进程对所有敏感数据的访问 → 完整的行为图谱
```

**用途 B：条件触发**
```
"当且仅当某条指令读某个地址时"执行动作
→ 精准的断点，无需 int3
```

## ★★ 4.7 缓存行为控制（Cache Behavior Control）

### 这是什么

**让同一份物理内存对不同的访问者呈现不同的缓存属性。**

```
我们的访问：非缓存（MmNonCached）→ 直接读物理，不经 cache
目标的访问：正常缓存 → 性能不受影响
```

### 为什么这是"狠"的

| 能力 | 宿主内核 |
|---|---|
| 设置内存缓存属性 | 能（但**全局**，影响所有访问者） |
| **按访问者区分** | **不能** —— PAT/MTRR 是物理地址级的 |

### 用途

**用途 A：无痕读取的强化**
```
非缓存读 → 不污染 cache → 目标进程的性能特征不变
→ 检测器无法通过"cache miss 模式异常"发现我们
```

**用途 B：侧信道防护/利用**
```
控制 cache 行为 → 影响时序侧信道
```

## Tier 4 汇总

| # | 能力 | 宿主能否做到 | 风险 | 依赖 |
|---|---|---|---|---|
| **4.1** | **视图分裂**（同一地址不同观察者看到不同内容） | ❌ 原理不能 | **高** | alt NPT（已有）+ Zen3 TLB 约束 |
| **4.2** | **时间维度**（O(1) 回滚、多版本共存） | ❌ | 中高 | npt_map_page（已有） |
| **4.3** | **跨进程物理别名**（单方面建立别名） | ❌ | 中 | npt_map_page + 目标 CR3 识别 |
| **4.4** | **指令级访问控制**（按 RIP 区分同一地址） | ❌ | 中 | NPF + GuestRip（已有） |
| **4.5** | **物理帧所有权接管** | ❌ | 中高 | 帧追踪 + 拦截释放 |
| **4.6** | **硬件断点超集**（无限监控点） | ❌ | 低 | npt_set_page_perm（已有） |
| **4.7** | **缓存行为控制**（按访问者区分） | ❌ | 中 | NPT 项属性（部分已有） |

**共同点**：**全部是"翻译层才能做的事"**。
宿主内核看到的永远是"物理内存就是物理内存"，
只有 hypervisor 站在 **GPA→SPA 的翻译点**上，才能让"同一个 GPA 对不同人呈现不同结果"。

## 为什么 Tier 4 才是"最狠的"

```
Tier 1-3 的命题：怎么把内存读写得更好
Tier 4 的命题：  让"内存"这个概念本身变得可控

Tier 1-3 相对 Engine A：更快、更隐蔽、更多类型
Tier 4 相对一切宿主方案：**做宿主原理上做不到的事**
```

**这是 hypervisor 存在的根本理由** —— 不是在宿主里做同样的事，
而是**在宿主看不到的那一层做宿主做不到的事**。

## 实施建议（Tier 4 单独成批）

```
第一批  Phase 1-5   核心引擎 + Tier 3 超越点        → v0.4.0
第二批  Phase 2b+6  自建映射 + 岛内执行             → v0.5.0
第三批  Phase 7     保护协同 + 共享窗               → v0.6.0
第四批  Phase 8     ★ Tier 4（虚拟化层独有能力）    → v0.7.0
```

**第四批的 Phase 划分**（按风险递增）：

```
Phase 8.1  硬件断点超集（4.6）          低风险  ← npt_set_page_perm 已有
Phase 8.2  指令级访问控制（4.4）        中风险  ← NPF + GuestRip 已有
Phase 8.3  时间维度（4.2）              中高风险 ← npt_map_page 已有
Phase 8.4  跨进程物理别名（4.3）        中风险
Phase 8.5  缓存行为控制（4.7）          中风险
Phase 8.6  物理帧所有权接管（4.5）      中高风险
Phase 8.7  ★ 视图分裂（4.1）            高风险  ← 最狠，放最后
```

**Phase 8.7 放最后的原因**：
- 它是 Tier 4 里最狠的（视图分裂）
- 但它撞上 **Zen3 NPT TLB 的已知限制**（9.297/9.298 证伪了软件冲刷）
- **前置研究**：先验证"静态视图分裂"（不同地址范围不同视图）是否可行
- 若动态切换不可行，**静态版本仍然有价值**（部分场景够用）

| 级别 | 数量 | 性质 | 相对 Engine A |
|---|---|---|---|
| Tier 1 | 6 | 同层替代 | 更快/更隐蔽 |
| Tier 2 | 4 | 跨层质变 | 宿主不可见 |

| **Tier 4** | **7** | **虚拟化层独有** | **宿主原理上做不到** |

```
Engine A       = 用内核的接口读写内存

Tier 4         = 让"内存"本身变成可编程的
```
